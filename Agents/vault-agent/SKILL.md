# Vault Agent

## Persona

Act as the secrets custodian. Keep secrets out of git, enforce least-privilege Vault policies, and make rotation observable before applying changed credentials to services. Treat every new or changed service as a secret review: if it needs credentials, API keys, tokens, signing secrets, encryption keys, webhook secrets, or bootstrap passwords, add those requirements to Vault and wire the service to consume Vault-rendered values.

## Service Contract

- Containers: `vault`, `vault-rotator`
- Internal endpoint: `http://vault:8200`
- Host endpoint: `http://localhost:${VAULT_HTTP_PORT:-8200}`
- FQDN: `vault.hq-sec.local`
- Config: `./The Shield/vault/config/vault.hcl`
- Policy: `./The Shield/vault/policies/secstack-rotator.hcl`
- Secret manifest: `./The Shield/vault/secrets/service-secrets.tsv`
- Rotation script: `./The Shield/vault/scripts/monthly-rotate.sh`
- Env render script: `./The Shield/vault/scripts/render-service-env.sh`
- Local rendered env: `.env.vault` ignored by git
- Volumes: `vault-data`, `vault-logs`, `vault-rotator-state`

## Workflow

1. Start Vault with `docker compose -f security-stack.compose.yml --profile secrets up -d vault`.
2. Initialize and unseal Vault on the deployment host; never commit unseal keys or root tokens.
3. Enable KV v2 at `${VAULT_KV_MOUNT:-secret}`.
4. Write the `secstack-rotator` policy and create a periodic token.
5. Place that token in local `.env` as `VAULT_ROTATOR_TOKEN`.
6. Start `vault-rotator` and inspect logs for monthly rotation status.

## Service Secret Workflow

1. When adding or changing any service/container, inspect its environment variables, config files, APIs, credentials, tokens, keys, webhook secrets, and bootstrap users.
2. If secrets are needed, add rows to `The Shield/vault/secrets/service-secrets.tsv` with service name, Vault path, env var, generator, and description.
3. Seed new paths with `The Shield/vault/scripts/seed-stack-secrets.sh` or let the monthly rotator create/update generated values.
4. Make the service reference the secret through a Vault-rendered variable in Compose or config. Prefer `.env.vault` generated by `The Shield/vault/scripts/render-service-env.sh` over committed values.
5. Keep `.env.example` as placeholders only; never put real values there.
6. Document new secret paths in `docs/vault-secrets.md` and any affected service docs.
7. Ensure monthly rotation covers the new paths through the manifest. Use `random` for generated values and `sha256:<path>` for derived Graylog-style hashes.

## Verification

```bash
docker compose -f security-stack.compose.yml --profile secrets exec vault vault status
docker compose -f security-stack.compose.yml logs --tail 100 vault-rotator
VAULT_ADDR=http://127.0.0.1:8200 VAULT_TOKEN=<operator-token> sh "The Shield/vault/scripts/render-service-env.sh" .env.vault
curl http://vault.hq-sec.local/v1/sys/health
```

## Safety

Do not store real tokens, unseal keys, root tokens, `.env.vault`, rendered `.env` files, or copied service passwords in the repository. Monthly rotation writes fresh values to Vault, but many services still need explicit operator-controlled reloads or restarts to consume rotated static credentials.

Read `references/rotation.md` before changing the rotation schedule or secret paths.
